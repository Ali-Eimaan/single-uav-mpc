# §14 · CI

**Governs:** `.github/workflows/{colcon_build,format_check,docker_smoke_test}.yml`
**Prerequisites:** [02_ENVIRONMENT.md §2.1](02_ENVIRONMENT.md) — **resolve V1–V3 before writing
a line of this.** Three of the nine risk-register rows are CI-only, and each fails before your
first real step executes.
**Milestone:** M8
**Done when:** criteria A1, A6 and A9 are green.

All jobs run on `ubuntu-26.04` in a `ros:lyrical-*` container.

**PEP 668 applies to every container-based job** — see
[02_ENVIRONMENT.md §2.3](02_ENVIRONMENT.md) for the venv decision. The `format_check.yml` python
job is the exception; it uses `actions/setup-python`.

## 14.1 `colcon_build.yml`

Cache pip, the acados build, and `build/`+`install/`, keyed on the lockfiles and
`codegen/ACADOS_COMMIT`. A 40-minute CI nobody waits for is a CI nobody trusts.

Run `generate_acados_solver.py --check-only` **before** the build so stale generated code fails
rather than being silently regenerated. `-DCMAKE_BUILD_TYPE=Release` is mandatory — the
solve-time assertions are meaningless otherwise. Upload test XML and the percentile JSON as
artifacts.

Ubuntu 26.04 ships a newer GCC than acados' CI baseline (risk V8). If blasfeo or hpipm fail to
compile, that is a toolchain issue, not your code — pin a newer acados commit rather than adding
`-w` or downgrading the compiler.

`px4_msgs` must be cloned at the branch matching `PX4_VERSION` from `docker_smoke_test.yml`
(risk V4). Pin both in one place and reference it here.

The `build-no-acados` job exists to catch an acados header leaking out of the wrapper. If it
starts failing, fix the leak — do not add the include path to that job.

## 14.2 `format_check.yml`

Under two minutes; it should be the first thing a contributor sees fail.

Put flake8 settings in the committed `setup.cfg`, never inline flags, or the local and CI runs
will drift. Install black/flake8 at the versions pinned in `requirements.txt` — do not restate
the version numbers in the workflow.

The `ros-lyrical-ament-cmake-*` linter debs may not be published yet (risk V3). If they are not,
install the ament linters from source into the venv rather than dropping the C++ lint job.

The `docs` job counts remaining `TODO(deepseek)` markers and reports the number as a job summary
— a progress meter, not a gate, until v1.0.

## 14.3 `docker_smoke_test.yml`

The differentiating job: PX4 SITL + Gazebo + the NMPC node actually fly, headless, inside the
container. Most comparable repositories do not build; this one hovers autonomously.

Build the sim image in a separate manually-triggered workflow, publish it to GHCR, and have this
job only **pull** — building PX4 on every push makes this 40 minutes and nobody will wait. The
image layers PX4 + Gazebo Jetty + acados onto `ros:lyrical-ros-base`.

Assertions live in `scripts/assert_hover.py` so they can be run locally:
`STATE_TRACKING` within 20 s; RMS error < 0.15 m; max error < 0.30 m; zero solver failures;
p99 solve < 5 ms (relaxed — a CI runner is not a flight computer); altitude never below half the
target. Print every metric even on success. Upload the bag, the ulog and the node logs with
`if: always()` — when this job fails you get exactly one shot at diagnosing it from the
artifacts.

The `figure8` job runs on schedule and `workflow_dispatch` only, not on every push; keep the
per-PR feedback loop short.

**Budget real effort for determinism here** — fixed seeds, bounded timeouts, no sleep-and-hope.
A smoke test that fails 30% of the time trains everyone to ignore red, which is worse than not
having one.
